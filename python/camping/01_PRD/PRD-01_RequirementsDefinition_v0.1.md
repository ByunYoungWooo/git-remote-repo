## ⚠️ 절대 원칙 (우선순위 최상위)

1. **본 문서 작성 및 검토 단계에서는 `res.knps.or.kr`에 접속/테스트를 일절 하지 않는다.** (사이트 기술 분석은 ⑦단계 이후, 허용 범위 안에서만)
2. **본인 명의 계정만** 사용한다. 타인 양도·대리 예약 금지 조항 준수.
3. **결제는 사용자가 직접** 수행한다. 결제 API 자동화 없음 (PCI 부담 회피 + ToS 리스크 최소화).
4. **반자동 우선**: 최종 확인·인증 단계는 Human-in-the-loop(사람 개입 지점)으로 설계.

## 2. 요구사항 상세 (2라운드 확정 사항)

### 2.1 예약 시점 & 재시도 정책
| 항목 | 확정 내용 | 비고 |
|------|-----------|------|
| **예약 오픈 전략** | 기본: **오픈 정각 즉시 자동 시도**(대기→열리자마자 사이트 검색/진행) + 옵션: 허용 시간 window 설정 (예: 09:00~12:00만 시도) | Q7 답변: a+c |
| **재시도** | 실패 시 **즉시 재시도, 최대 3회** (간격 최소/무시) | Q8 답변: a — "사이트 선점" 특성에 맞춘 빠른 재시도. ⑫단계에서 세션 만료 등 장애 유형별 간격 예외 정의 예정 |

### 2.2 알림 정책
| 항목 | 확정 내용 | 비고 |
|------|-----------|------|
| **성공 시** | Telegram으로 **즉시 상세 알림** — 사이트명/날짜/입실시간/예약번호 등 (결제 전 상태까지 도달하면 "결제 필요" 명시) | Q9 답변: a — 추가 채널(문자/이메일)은 v1 제외 |
| **실패 시** | 매 실패마다 Telegram으로 **사유 + 다음 시도 시간** 통보, 최종(3회 모두 실패) 시 "일일 종료" 알림 1회 | Q10 답변: a — 로그에도 전량 기록 (FR-009) |

### 2.3 사람 개입 지점 (Human-in-the-loop)
| 단계 | 방식 | 비고 |
|---|---|---|
| 로그인/세션 유지 | **자동** — 가능한 부분은 자동화 원칙 | Q11 확정 (출석부 테스트 환경에서 먼저 검증, §2.4) |
| 예약자 정보 입력(성명·연락처) | **자동** (사전 등록값 사용) | Q11 확정 |
| 본인인증(휴대폰 인증번호) | **사람 수행** → 시스템이 "🔔 인증 필요" 알림 후 사용자 처리, 완료 시 자동 이어서 진행 | 방법론 ⑩단계 구조 |
| 결제 | **사람 수행** (직접 입금/PG), 시스템은 결제 절차까지 진행만 지원 | 절대 원칙 #3 — 결제 자동화 없음 |

### 2.4 테스트 환경 전략 ⭐

> 형 지시 (2026-09-25): "로그인 과정 등 가능한 부분은 출석부 페이지에서 먼저 테스트한다"

| 항목 | 내용 |
|------|---|
| **테스트 대상** | 출석부 시스템 `http://127.0.0.1:8000/clock.php` (로컬, 우리 소유) — 기동 방법: `cd /home/wooba/source/php/attendance/public && php -S 0.0.0.0:8000` |
| **용도** | 로그인 플로우(아이디/비밀번호 입력→제출→세션 확인), 요소 선택, 폼 제출 등 브라우저 자동화 기술의 **연습장** |
| **원칙** | `res.knps.or.kr`에는 실제 필요 시점(방법론 ⑦단계 기술 분석 이후)에 최소한의 접근만. 그 전까지 모든 자동화 테스트는 로컬 출석부에서 수행 |
| **연결고리** | 방법론 ⑫단계 "실제 예약을 발생시키지 않는 테스트 환경부터 검증" + 기존 `OLD/1_PRD.txt`의 "1차 테스트(attendance) 완료" 성공 지표와 동일 방향 |

### 2.5 개발 방식 원칙 ⭐

> 형 지시 (2026-09-25): "개발은 가능한 소규모 모듈로 분리해서 진행한다"

| 항목 | 내용 |
|------|---|
| **모듈 분리기** | 기능 단위(로그인 / 검색 / 사이트 조회 / 예약 진행 / 알림 / 재시도)별 **소형 독립 모듈**로 개발. 한 모듈이 너무 많은 일을 하지 않도록 경계 유지 |
| **독립 검증** | 각 모듈은 출석부 테스트 환경 또는 mock으로 **단독으로 실행·검증 가능해야 함**. 전체 파이프라인이 완성된 뒤에야 첫 동작을 확인하는 구조 금지 |
| **진행 방식** | 모듈 완료 → 테스트 통과 → 다음 모듈 순차 연결 (방법론 ⑧단계 프로토타입 "사이트 상태 읽어오기"가 첫 완성 모듈) |
| **이유** | 장애 시 원인 격리가 쉽고, 실패한 부분만 재개발하면 됨. KNPS는 외부 사이트라 섹션별 진행이 필수 |

### 2.6 예약 조건 & 운영 세부사항 (3라운드 확정)
| 항목 | 확정 내용 | 비고 |
|------|-----------|------|
| **동시 예약** | **여러 후보 병렬 시도 허용** — 같은 날 A/B 사이트 등 여러 후보를 동시에 진행 가능 | Q13: b ⚠️ KNPS 동시접속/정책 위반 가능성 → 방법론 ④단계(제약 분석)에서 허용 범위 재확인 필요. 기본은 2개까지, 1개만 유지하는 안전모드 옵션 제공 예정 |
| **세션 관리** | 로그인 후 **세션 유지 + 만료 시 자동 재로그인** (매 실행마다 재로그인 금지 — 부하/위험 최소화) | Q14: a |
| **운영 시간대** | 제한 없음 (24시간 시도 가능) | Q15: a ⚠️ 다만 ④단계에서 오픈 정책 확인 시 조정 가능 |

### 2.7 예약 정보 사전 등록 (Q12 — 부분 미답)
> 형이 명시하지 않은 기본안으로 설계합니다. 다르면 말씀 주세요.
- 성명, 연락처(휴대폰), 동행 인원 수, 차량 대수 → 설정 파일/DB에 사전 등록 후 자동 입력
- 그 외(장비·반려동물 등)는 v1에서 폼 필드에 따라 선택 입력 처리
