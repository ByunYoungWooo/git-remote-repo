## 1. 전체 흐름도 (Happy Path)

```
[예약 정보 사전 등록: 날짜 후보/공원/야영장/사이트 우선순위]
        │
        ▼
① 예약 오픈 시간 대기 ────────────── (자동, 정각 즉시 시도 + window 옵션)
        │
        ▼
② 사이트 접속 (res.knps.or.kr) ─── (자동)
        │
        ▼
③ 로그인 ───────────────────────── (자동 / 세션 유지 + 만료 시 자동 재로그인)
        │
        ▼
④ 예약 메뉴 진입 → 시설(야영장) 선택 ─ (자동, 사전 등록 공원/시설)
        │
        ▼
⑤ 날짜 후보 순서로 검색 ──────────── (자동: 특정일 모드 or 범위 모드)
        │
        ▼
⑥ 예약 가능 여부 확인 ───────────── (자동: 사이트별 상태 조회)
        │  ▲◄────────────────────────┐
        ▼                            │
⑦ 우선순위 사이트 선택 (1→2→3순위) ──┘ (자동, 실패 시 다음 후보/날짜로 이동)
        │
        ▼
⑧ 예약 진행: 날짜·사이트·인원 입력 (자동, 사전 등록값 자동 입력)
        │
        ▼
⑨ 본인인증(휴대폰 인증번호) ──────── 🔔 사람 수행 — 시스템 "🔔 인증 필요" 알림 후 대기
        │  ▲ 사용자가 완료 → 시스템 감지
        ▼
⑩ 결제 ──────────────────────────── 🔔 사람 수행 — 직접 입금/PG (결제 자동화 ❌ 절대 원칙 #3)
        │
        ▼
⑪ 예약 상태 확인(확정 여부 검증) ─── (자동, 조건부: ⑩ 완료 후)
        │
        ├── 성공 → ⑫ Telegram 상세 알림 (사이트/날짜/예약번호 + "결제 완료까지 처리" 안내)
        │
        └── 실패 → 재시도 정책 적용 (즉시×3회, 매 회 사유+다음시도시간 통보)
                    └ 최종 실패 → "당일 종료" 알림 1회 + 로그 전량 기록
```

## 2. 단계별 자동화 구분표 ⭐

| # | 단계 | 동작 내용 | 분류 | 근거 (PRD 기준) | 검증/확인 포인트 |
|---|------|-----------|------|-----------------|------------------|
| ① | 오픈 시간 대기 | 정각까지 대기, 오픈 즉시 진입 시도. window 옵션(예: 09~12시만) 가능 | **자동** | PRD §2.1 (Q7: a+c) | KNPS 실제 오픈 시점 규칙 → ④단계 확인 (OI-2와 연결) |
| ② | 사이트 접속 | URL 접근, 페이지 로드 완료 대기 | **자동** | — | 페이지 로딩 실패 시 처리 → 방법론 ⑫단계 |
| ③ | 로그인 | ID/PW 입력→제출→로그인 성공 판정. 세션 유지, 만료 감지 시 자동 재로그인 | **자동** (조건부: 인증번호 요구 시 사람) | PRD §2.3 Q11 확정 / §2.6 Q14(a) | KNPS 로그인에 별도 OTP가 붙는지 → ④단계 확인 (있으면 해당 지점만 사람) |
| ④ | 메뉴·시설 선택 | 예약 메뉴 진입, 사전 등록된 공원/야영장 선택 | **자동** | PRD §1 범위(Q1: b — 야영장+기타) | 사이트 구조(HTML/API) → ⑦단계 기술 분석 |
| ⑤ | 날짜 검색 | 날짜 후보 순서대로 검색 / 또는 기간 범위 검색 | **자동** (조건부: 모든 날짜 불가 → 당일 종료 알림) | PRD §1 Q4(c) 두 모드 지원 | "예약 오픈되지 않은 날짜" 표시 방식 확인 → ⑦단계 |
| ⑥ | 가능 여부 확인 | 사이트별 예약가능/불가 상태 읽기 | **자동** | 방법론 ⑧프로토타입 = 이 단계 성공이 첫 목표 | 상태 판정 기준(텍스트/클래스/API) → ⑦단계 |
| ⑦ | 사이트 선택·이관 | 우선순위 순 시도, 실패 시 다음 순위 자동 이관 (최대 후보 수 제한) | **자동** | PRD §1 Q5(a), OI-1(병렬 옵션 안전모드 포함) | 병렬 시도 허용 범위 → ④단계 ToS 확인 |
| ⑧ | 예약 정보 입력 | 성명/연락처/인원/차량 등 사전 등록값 자동 입력 | **자동** | PRD §2.7 (Q12 기본안, OI-3) | 폼 필드 실체 → ⑦단계 분석 시 확정 |
| ⑨ | 본인인증 | 휴대폰 인증번호 수신→입력 — **사용자 직접**. 시스템은 "🔔 인증 필요" 알림 후 대기, 완료 감지 후 자동 진행 | **사람 수행** (완료 감지는 자동) | PRD §2.3 Q11, 방법론 ⑩단계 HITL 구조 | 인증 만료 시간(예: 5분) → 대기 정책 결정: 만료 시 재요청 or 중단? → ③단계에서 FR으로 명시 |
| ⑩ | 결제 | 직접 입금/PG — **사용자 직접**. 시스템은 결제 화면 도달까지 진행만 지원 | **사람 수행** (결제 자동화 ❌) | PRD 절대 원칙 #3 | 결제 후 상태 반영 방식(입금 확인 수동?) → 운영 프로세스 문서에서 정리 예정 |
| ⑪ | 상태 검증 | 결제 완료 후 예약 확정 여부 확인(예약번호/확정 문구) | **자동** (조건부: 미확인 상태 지속 시 재확인 N회 후 사람이 체크하도록 알림) | — (추가요구, 형 승인 대기) | 확인 로직 기준 → ⑦단계 분석 |
| ⑫ | 성공 알림 | Telegram 상세 통보: 사이트/날짜/시간/예약번호 + 남은 절차 안내 | **자동** | PRD §2.2 Q9(a) | — |
| ⑬ | 실패 처리·재시도 | 즉시 재시도 최대 3회, 매 회 "사유+다음 시도 시간" 통보, 최종 종료 알림 | **자동** | PRD §2.1-2.2 (Q8/Q10) | 세션 만료 등 장애 유형별 간격 예외 → 방법론 ⑫단계 문서에서 상세화 |

## 3. 조건부 자동화 로직 요약

```
조건부 A — 사이트 선점:
    선택한 사이트 "예약불가" 감지
      └→ 다음 우선순위 사이트로 즉시 이동 (같은 날짜)
           └→ 후보 소진 → 다음 날짜 후보로 이동
                └→ 모든 날짜 불가 → 당일 종료 + 알림

조건부 B — 세션 만료:
    로그인 상태 유실 감지
      └→ 자동 재로그인 1회 후 원래 단계로 복귀
           └→ 재로그인 실패 → "세션 복구 필요" 사람 알림

조건부 C — 인증/결제 (사람 단계):
    🔔 Telegram으로 지시 + 대기(타이머)
      └→ 완료 감지 → 자동 계속 진행
      └→ 대기 시간 초과 → 재알림 1회 → 그래도 불가하면 중단 + "수동 처리 필요" 보고

조건부 D — 병렬 후보 (OI-1):
    기본 안전모드: 동시 1건 순차
    확장 모드: 최대 N개 병렬 (④단계 ToS 확인 후만 활성화)
```

## 4. 테스트 매핑 (출석부 환경, PRD §2.4 기준)

| 자동화 구분표 단계 | 출석부(`http://127.0.0.1:8000`)에서 검증 가능한 부분 |
|---|---|
| ③ 로그인 | index.php → clock.php 이동까지의 입력/제출/세션 판정 플로우 전체 (첫 프로토타입 후보) |
| ⑧ 폼 정보 입력 | 출석 체크 폼 등 입력 필드 자동 채움 연습 |
| 조건부 B(세션 만료) | 세션 만료 시 재로그인 루프 시뮬레이션 |
| ⑥ 가능 여부 확인 | 존재/비존재 요소 판정 로직(mock 페이지로) 검증 |

> 원칙: `res.knps.or.kr`에는 이 문서 단계에서 **접근하지 않는다** (절대 원칙 #1).
> 위 검증은 전부 로컬 출석부 + mock으로 수행.
