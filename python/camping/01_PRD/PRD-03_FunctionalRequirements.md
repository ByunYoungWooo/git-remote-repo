## 1. 기능 요구사항 (Functional Requirements)

> 규칙: FR = 필수(MUST), SF = 선택(Should, v1 범위 내 우선순위 낮음)
> 검증 기준은 "출석부 환경 또는 mock에서 검증 가능" 기준으로 작성 (PRD-02 §4 매핑 원칙)

### 1.1 로그인 & 세션

| ID | 요구사항 | 상세 | 우선순위 |
|----|----------|------|----------|
| **FR-001** | 로그인 | 사전 등록한 ID/PW로 KNPS 계정에 자동 로그인하고, 성공 여부를 판정한다 (세션 쿠키/페이지 상태 기준) | MUST |
| **FR-002** | 세션 유지 & 복구 | 로그인 후 세션을 재사용한다. 세션 만료 감지 시 자동 재로그인 1회, 실패 시 "세션 복구 필요" 사람 알림 (PRD-02 조건부 B) | MUST |
| SF-003 | 세션 상태 보고 | 세션 유효/만료 상태를 로그·Telegram에 기록 | Should |

### 1.2 검색 & 조회

| ID | 요구사항 | 상세 | 우선순위 |
|----|----------|------|----------|
| **FR-004** | 야영장(시설) 검색 | 사전 등록한 공원/야영장을 예약 메뉴에서 자동 선택한다 (야영장 + 기타 시설 지원, PRD §1 Q1: b) | MUST |
| **FR-005** | 날짜 검색 — 특정일 모드 | 날짜 후보 목록(최대 3개 기본)을 순서대로 검색한다 | MUST |
| SF-006 | 날짜 검색 — 범위 모드 | "YYYY-MM-DD ~ YYYY-MM-DD" 기간 내 가능 일자 조회 (PRD §1 Q4: c) | Should |
| **FR-007** | 예약 가능 사이트 조회 | 선택한 날짜의 사이트별 상태(예약가능/불가)를 목록으로 읽어온다 — **방법론 ⑧단계 프로토타입 = 이 요구사항 달성** | MUST |

### 1.3 예약 진행 (Engine)

| ID | 요구사항 | 상세 | 우선순위 |
|----|----------|------|----------|
| **FR-008** | 사이트 우선순위 처리 | 사이트 후보를 지정된 순서(1→2→3...)로 시도, 실패 시 다음 순위로 자동 이관. 후보 소진 시 다음 날짜 후보 이동 (PRD §1 Q5: a) | MUST |
| SF-009 | 병렬 후보 모드 | 여러 후보 동시 시도 (기본 **안전모드: 동시 1건**, 확장 모드는 OI-1 ToS 확인 후에만 활성화 가능 — PRD-02 조건부 D) | Should |
| **FR-010** | 예약 정보 자동 입력 | 사전 등록값(성명/연락처/인원/차량)을 예약 폼에 자동 입력한다 (PRD §2.7 기본안, OI-3 — 형 변경 시 업데이트) | MUST |
| **FR-011** | Human-in-the-loop 제어 | 사람 단계(본인인증·결제) 도달 시: ①Telegram "🔔 처리 필요" 알림 ②완료 감지 대기(**5분**, C-1 승인) ③완료→자동 진행 / 초과→재알림 1회(**3분 추가**) 후 중단+보고 (PRD-02 조건부 C, W-1 → **C-1 확정**) | MUST |
| **FR-012** | 접수 완료 검증 | 예약 제출 후 성공 여부(성공 화면 도달·예약번호 등 핵심 정보 추출) 확인 + Telegram 상세 전달. **결제 및 이후 단계의 상태 추적은 범위 외** (형 지시 2026-09-27: 예약까지가 목표, W-2 제거) | MUST |

### 1.4 재시도 & 장애 처리

| ID | 요구사항 | 상세 | 우선순위 |
|----|----------|------|----------|
| **FR-013** | 예약 재시도 | 실패 시 **최대 2회 재시도(총 시도 상한 3회), 간격 30~60초 랜덤**. NetFunnel 가상 대기 팝업(`NETFUNNEL_WAIT`)·차단 신호 감지 시 즉시 중단+보고. CAPTCHA는 FR-013b 정책 적용 (PRD §2.1 개정, Q-2(a) 확정 2026-09-27) | MUST |
| **FR-013b** | CAPTCHA 처리 | 야영장 플로우 "자동예약 방지숫자" 이미지: OCR 자동 인식·입력 **최대 2회(리프레시 포함)** → 실패 시 🔔 HITL 알림 후 사람 입력 대기(C-1 패턴) (Q-1(b) 형 확정 — 리스크 인지 후 승인, stealth ❌ 유지) | MUST |
| **FR-014** | 장애 유형별 처리 | 페이지 로딩 실패 / 네트워크 오류 / 세션 만료 / 사이트 선점 / 서버 응답 지연 / 브라우저 종료 — 각각의 감지·복구 전략을 정의하고 적용한다 (방법론 ⑫단계, 세부 정책은 ⑫단계 문서에서) | MUST |
| **FR-015** | 실패 로그 기록 | 모든 시도(성공/실패)에 대해 단계별 타임라인 + 실패 사유를 로그 파일과 DB(또는 SQLite)에 전량 기록 (PRD §2.2 Q10: a) | MUST |

### 1.5 알림

| ID | 요구사항 | 상세 | 우선순위 |
|----|----------|------|----------|
| **FR-016** | 성공 알림 | Telegram 즉시 상세 통보 — 사이트명/날짜/입실 시간/예약번호 + 남은 절차(결제 등) 안내 (PRD §2.2 Q9: a) | MUST |
| **FR-017** | 실패 통보 | 매 실패마다 "사유 + 다음 시도 시간" 통보, 최종 3회 실패 시 "당일 종료" 알림 1회 (Q10: a) | MUST |
| SF-018 | 사람 단계 대기 중 상태 보고 | 인증/결제 대기 시작·타임아웃 발생 시 Telegram에 상황 전파 (**C-1 확정** 연동: 5분→재알림→중단) | Should |

### 1.6 운영/구성

| ID | 요구사항 | 상세 | 우선순위 |
|----|----------|------|----------|
| **FR-019** | 예약 요청 구성 파일 | 날짜 후보 / 공원·시설 / 사이트 우선순위 / 인원·차량 / **오픈 일시(시설별 공지 기준)** 를 설정(파일 또는 SQLite)에서 사전 등록하고, 실행 시 로드한다 (PRD-04 C-5: 고정 시각 가정 금지 — P-3 근거) | MUST |
| SF-020 | 실행 트리거 모드 | ①수동 실행(명령 1회) + ②일정 자동 실행(APScheduler/systemd timer, 방법론 ⑬단계 연동) — v1은 ① 보장, ②는 운영 단계에서 | Should |

## 2. 비기능 요구사항 (Non-Functional Requirements)

> 방법은론: "성능 / 안정성 / 재시도 / 로그 / 보안 / 개인정보 / 장애 복구" — 이 항목 그대로 매핑

| ID | 영역 | 요구사항 | 상세/수치 목표 |
|----|-------|----------|----------------|
| **NFR-01** | 성능 | 응답 대기 시간 상한 | 페이지 로드·요소 대기 30초 기본 타임아웃 (기존 config.py 기준), 초과 시 재시도 정책 적용. 정각 오픈 시도 시 진입까지 ≤5초 목표(네트워크 조건 내) |
| **NFR-02** | 안정성 | 반복 실행 안전성 | 같은 예약 요청을 2회 이상 중복 진행하지 않음 — "진행 중" 락(파일/DB flag)으로 가드. 프로세스 크래시 후 재실행 시 이전 상태 복원 가능 (멱등성 원칙) |
| **NFR-03** | 부하 최소화 | KNPS 요청 절제 | 동시 브라우저 1개, 무의미 반복 리로드 금지, 인위적 지연 최소 2초 (기존 `OLD/1_PRD.txt` 성공 지표 계승). 재시도 간격은 FR-014 정책이 우선 |
| **NFR-04** | 재시도 | 재시도 정책 일관성 | 총 시도 상한 3회 + 간격 30~60초 랜덤 + 차단 신호(가상 대기/NetFunnel) 즉시 중단 — FR-013/FR-014와 일치, **무한 루프 금지** (Q-2(a) 개정 2026-09-27) |
| **NFR-05** | 로그 | 전량 로깅 | INFO(진행 흐름)/WARN(재시도·복구)/ERROR(실패) 등급, 각 시도별 타임라인, 파일 + 구조화(SQLite) 이중 기록. 로그에 비밀번호·인증번호 원문 ❌ (해시/마스킹) |
| **NFR-06** | 보안 | 자격증명·민감정보 보호 | ID/PW는 `.env` 또는 OS 키체인에서만, 코드·로그에 하드코딩 금지. 저장된 민감정보 파일은 권한 600, `.gitignore` 적용 확인 (기존 attendance 패턴 계승) |
| **NFR-07** | 개인정보 | 수집 범위 확정 | 예약자 개인정보(성명/연락처/**주민번호 포함**, C-5 확정 2026-09-27 — KNPS 자동 입력 완전성)는 본인 명의 1건만 `.env` 전용으로 저장하며, 목적은 자동 입력 재사용으로 한정. 로그·텔레그램 알림에 주민번호 원문 출력 **절대 금지** (마스킹: 성/이름 일부 + 연락처 마지막 4자리 표시) |
| **NFR-08** | 장애 복구 | 프로세스 복구 | systemd `Restart=on-failure` + 시작 시 "이전 실행 상태" 점검(진행 중 락 감지 → 사람 보고). Telegram으로 기동/종료 알림 (방법론 ⑬단계) |
| **NFR-09** | 가시성 | 실행 상태 조회 | `status`(명령 또는 파일)로 현재 단계·대기 상태·최근 시도를 확인할 수 있어야 함 — 사람이 인증 중인지, 시스템이 대기 중인지 한눈에 확인 |
| NFR-10 | 모듈성 | 소규모 모듈 분리 | PRD §2.5 원칙: 로그인/검색/조회/진행/알림/재시도 독립 모듈, 각 모듈 단독 테스트 가능 (pytest) |

## 3. 범위 외 선언 (v1 Non-Goals — 명확히 못 박음)

| 항목 | 이유 |
|------|------|
| 자동 결제(PG 연동) | 절대 원칙 #3 + PCI 부담 |
| **예약 완료 후 상태 추적(결제·확정 대기 등)** | 형 지시 2026-09-27 — 목표는 **예약 접수 완료까지**, 이후 처리는 사용자 직접 (C-2/C-3 확정) |
| 타인/다중 계정 예약 | ToS 위반 가능성, PRD Q6: a |
| SMS/이메일 채널 | v1은 Telegram 단일 채널 (Q9: a), 확장 시 재평가 |
| KNPS 서버 부하 시험·대량 스크레이핑 | 절대 원칙 #1 — 최소 접근만 |
| 추첨제 자동 응모 로직 상세화 | OI-2 — ④단계 정책 분석 후 범위 확정. v1은 "응모 페이지 도달까지" 지원까지만 설계 |
